# Install Strategy — making `tekt.catalog.yaml` the source of truth (Issue #83)

`install.sh` is ~3,000 lines and `install.ps1` ~2,300, and the two encode the same
knowledge twice: which tools exist, what layer they belong to, how to detect them,
and how to install them. `tekt.catalog.yaml` already lists every tool with `cmd`,
`install`, `install_macos/_linux/_windows` and `upstream`, but nothing read those
fields at install time — the catalog described the world and the scripts rebuilt it
by hand.

The constraint that decides everything below: the entry point must stay

```
curl -fsSL https://tekt.md/install.sh | bash
irm https://tekt.md/install.ps1 | iex
```

on a machine with nothing installed. No runtime, no package manager, no YAML
parser, no agent. Anything that needs to be installed before Tekt can install
things is disqualified as the *bootstrap*, however good it is afterwards.

## What the installers actually do today

Most `install_*` functions are not package installs — they are a thin, careful
wrapper around somebody else's official installer:

| Tool | What `install.sh` runs |
| --- | --- |
| Homebrew | `/bin/bash -c "$(curl -fsSL .../Homebrew/install/HEAD/install.sh)"` |
| Python | `curl -fsSL https://pyenv.run \| bash`, then `pyenv install` |
| Node | `curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v$NVM_VERSION/install.sh \| bash` |
| Docker | `curl -fsSL https://get.docker.com -o /tmp/get-docker.sh && sh /tmp/get-docker.sh` |
| rclone | `curl https://rclone.org/install.sh \| $SUDO bash` |
| Claude Code | `curl -fsSL https://claude.ai/install.sh \| bash` |

That delegation is the right call and is not up for debate here: upstream owns
platform detection, checksums, and code-signing, and Tekt inherits their fixes for
free. What it means for this issue is that **the value of a config-management
system is small** — nearly every "resource" would be a `shell`/`command` module
wrapping the same curl pipeline, so we would pay a tool's whole cost to gain
almost none of its declarative power.

The genuinely script-shaped work that remains is: ordering (Dev → Base → Edge →
Iris → Cloud), detection (`command_exists` / `Test-Cmd`), PATH repair
(`reload_path` / `Refresh-SessionPath`), keep-going resilience (`|| warn`), and
winget's exit-code/"Pending" reporting. None of that is expressible in YAML; all
of it is reusable across every tool. So the duplication to kill is the *per-tool*
imperative code, not the harness.

## Options

Scored 1–5 (5 best). "Official installers" = how well the option handles tools
whose install is a vendor script we must not replace.

| | Zero-prereq bootstrap | macOS/Linux/WSL2/Windows | Idempotent | Version pinning | Maintenance | Official installers |
| --- | --- | --- | --- | --- | --- | --- |
| **(a) bash/pwsh, loop generated from the catalog** | **5** | **5** | 4 | 4 | **4** | **5** |
| (b) Ansible | 1 | 3 | 5 | 4 | 2 | 3 |
| (c) Nix / Home Manager | 1 | 2 | 5 | 5 | 2 | 1 |
| (d) mise / asdf, runtime pins only | 3 | 4 | 4 | **5** | 4 | 4 |
| (e) devbox / devcontainer | 1 | 3 | 5 | 5 | 3 | 2 |

### (a) Keep bash/pwsh, drive the loop from the catalog

Both scripts stay single-file and dependency-free; they gain a ~40-line reader
(awk in bash, a line-regex parser in PowerShell) and one generic install function
each. Adding a simple tool becomes a catalog entry, not two code edits.

- Bootstrap: unchanged. awk is in POSIX base systems; the PowerShell reader uses
  only `[IO.File]::ReadAllLines` and `-match`.
- Cross-platform: the existing `install_macos/_linux/_windows` fields already
  encode the differences; the reader picks `install_<os>` then falls back to
  `install`.
- Idempotency: unchanged — same `command_exists` / `Test-Cmd` guard, now driven by
  `cmd:`/`detect:` from the catalog.
- Pinning: the `pins:` block already exists and is now read by a real parser
  instead of fixed `grep`/`sed` and three regexes.
- Cost: we own the reader. It is deliberately small: flat 8-space scalars only, no
  anchors, no nested maps, no flow collections — a subset the catalog already
  writes and the coverage check enforces.
- Official installers: perfect fit — the catalog field simply *is* the curl line.
- Weakness: it is a parser we maintain, and truly branchy installers (Homebrew on
  two architectures, pyenv build deps, Docker repo keys, Claude Desktop's
  fingerprint check) do not fit one line of YAML.

### (b) Ansible

Real idempotency, good inventory model, mature. But it needs Python plus a pip
install before it can do anything, which breaks `curl | bash` on a fresh box, and
Windows targets need WinRM/pywinrm and are second-class. Since most tasks would be
`ansible.builtin.shell: curl … | bash` with a `creates:` guard, we would trade a
500-line duplication problem for a runtime prerequisite and a second language.

### (c) Nix / Home Manager

Best pinning and reproducibility of anything here, and worst fit for this project:
no native Windows (WSL2 only), a multi-user daemon install as a prerequisite, and
a philosophy that is the opposite of "run the vendor's installer" — Tekt would
have to wait for nixpkgs to carry every agent (Claude Code, opencode, crush, pi,
omp) rather than tracking upstream the day it ships. Worth revisiting only as an
*optional* alternate profile for people who already run Nix.

### (d) mise / asdf for runtime pins only

Narrow scope, which is why it scores well: it replaces the hand-rolled Go tarball,
pyenv, and nvm logic (`install.sh` ~358–466) with `mise use -g go@1.26.2` etc., and
`mise.toml` could be generated from the catalog `pins:` block. asdf needs git+bash
plus a plugin per runtime; mise is a single static binary, so mise is the better of
the two. Native Windows support is the catch (see the recommendation below).

### (e) devbox / devcontainer

Excellent for a per-project dev shell, wrong layer for Tekt. devbox is Nix with a
nicer face and inherits (c)'s bootstrap and Windows problems; devcontainers need
Docker *first* and give a container, whereas Tekt is explicitly installing tools on
the user's own machine (Ollama, Tailscale, Claude Desktop, rclone mounts). Both
belong in the "Tekt inside a container" story, not in the installer.

## Recommendation

**Adopt (a), hybrid.** Each catalog entry declares who owns it:

- `managed: catalog` — installed by the generic loop from `install`/`install_<os>`,
  `cmd`/`detect`, `requires`, `install_alt`, `post_install`.
- `managed: script` — still installed by its `install_*` / `Install-*` function,
  which the entry names in `installer` / `installer_windows`, with prose
  `install_steps*` fields for documentation (never executed).

This gets the duplication down where it is pure boilerplate while leaving the
branchy, security-sensitive installers exactly as they are. Tools move from
`script` to `catalog` one at a time, each move deleting a function rather than
rewriting the installer in one risky sweep. `scripts/check-catalog.js`
(`npm run catalog:check`) fails the build if a function has no catalog entry, if an
entry has no way to detect or install itself, or if `install_order` drifts from the
layers — so the catalog cannot silently stop being the source of truth.

### Should mise replace the Go/pyenv/nvm logic?

**Yes on macOS/Linux/WSL2, as an opt-in, and no for the Windows bootstrap.**

Rationale: `install.sh` currently hand-rolls three different runtime managers —
a Go tarball with arch detection, pyenv (which compiles CPython and needs build
deps), and nvm — roughly 110 lines that exist only to honour three numbers in
`pins:`. mise covers all three with one static binary, gives per-project pinning
for free, and reads the same version numbers.

Why not as the default bootstrap:

- Windows native has no pyenv/nvm path at all today; it installs
  `Python.Python.3.12`, `OpenJS.NodeJS.LTS` and `GoLang.Go` through winget. mise
  on native Windows works for some backends but is markedly less exercised than on
  Unix, and shims interact badly with winget-installed runtimes on `PATH`. Windows
  should keep winget; WSL2 gets the Unix path, which is what the installer already
  recommends.
- `pyenv install` compiles; `mise use python@3.14` prefers precompiled builds —
  a real win, but a behaviour change (different Python build provenance) that
  deserves its own PR and its own testing, not a rider on this one.

Suggested sequencing: land the catalog loop first (this PR), then a follow-up that
adds `TEKT_RUNTIME_MANAGER=mise` honoured by `install_go`/`install_python`/
`install_nvm_node` on Unix, generating `~/.config/mise/config.toml` from `pins:`;
keep the current code as the default until the mise path has run on macOS, Ubuntu,
and WSL2. Never make mise a prerequisite — if it is absent, fall back to today's
logic.

## What this PR implements

- Install schema documented at the top of `tekt.catalog.yaml`, plus
  `install_order: [tekt.dev, tekt.base, tekt.edge, tekt.iris, tekt.cloud]`.
- Every tool entry carries `key`, detection (`cmd`/`detect`), install commands or
  prose `install_steps*`, `managed`, and the owning `installer` /
  `installer_windows` function.
- `install.sh`: `catalog_pin_rows` / `catalog_rows` (awk) replace the `grep`/`sed`
  pin loader; `catalog_install_one`, `catalog_install_layer`, `catalog_plan`.
- `install.ps1`: `Get-CatalogPins` / `Get-CatalogInstallEntries` replace the three
  regexes; `Install-CatalogEntry`, `Install-CatalogLayer`, `Show-CatalogPlan`,
  keeping `Install-Winget`'s exit codes and Pending reporting via the
  `winget:<Package.Id>` install form.
- `main()` / `Main` call `catalog_install_layer <layer>` at the head of each layer,
  in the existing Dev → Base → Edge → Iris → Cloud order, before the remaining
  script-managed functions.
- New commands on both: `catalog plan` (what the catalog would do here) and
  `install <tool>` (one catalog tool). All existing subcommands are untouched.
- Demonstrated end to end for Claude Code, opencode, crush, pi and omp.
